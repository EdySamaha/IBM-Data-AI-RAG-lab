## Opening · the architecture

**15 minutes.** Log in to watsonx.data and open your (empty) watsonx.ai project.
Then take in the shape of what you're about to stand up — see
[`docs/architecture.md`](../../docs/architecture.md) for the diagram. One diagram,
three boxes, one arrow of trust, and today you build all three:

- **watsonx.data** — an open lakehouse with a trusted catalog. Presto/Prestissimo
  queries Iceberg tables (and other sources) in place, no ETL, no copies.
- **Milvus** — a vector database in the same platform for semantic search / RAG
  over unstructured text (today, a PDF).
- **watsonx.ai** — the runtime where notebooks and Granite foundation models run,
  reading the catalogued data through a governed connection.

**The claim to prove today:** you could rebuild each box tonight with Postgres, a
Jupyter kernel, and a hosted model API. What you *couldn't* easily rebuild is the
property this lab demonstrates — the data never leaves your organization's
governed environment, and one access/lineage fabric spans both the data and the
AI. At each step, notice that the data is read where it sits and the model is
given only a schema and a question, never the rows themselves.

## watsonx.data · set up & explore

**30 minutes.** Create the trusted catalog, both engines, and the data table,
then query it in place. You stand the vector database up here but leave it empty
— you'll load the PDF into it from watsonx.ai in the next segment, since the
embedding happens with a watsonx.ai model. **Create the engines early** so they
reach *running* while you ingest the data.

### 1 · Create a trusted catalog

- In watsonx.data, open **Infrastructure manager** and add (or associate) a
  catalog — this is the governed container that will hold your table. This lab
  assumes a catalog named **`iceberg_data`**.
- If prompted, back the catalog with the storage bucket provided for the lab. The
  catalog is what makes the data trusted: access, lineage, and metadata are
  managed here, not scattered across copies.

### 2 · Create a SQL (Presto) engine

- Choose **Add component → Presto** (or Prestissimo). Give the engine a
  recognizable name (e.g. `lab-presto`), pick the smallest available size, leave
  the defaults, and click **Create**.
- Associate the engine with your `iceberg_data` catalog so it can query the table
  you're about to load.
- The engine takes a few minutes to reach *running*. Start it now and move
  straight on while it warms up — don't wait on this screen.

> 📎 Reference — [watsonx-ai-samples — Presto / lakehouse examples](https://github.com/IBM/watsonx-ai-samples)

### 3 · Create a vector database (Milvus)

- Still in Infrastructure manager, choose **Add component → Milvus**. Name it
  (e.g. `lab-milvus`), pick the smallest size, and click **Create**. It starts
  out empty — there's no PDF-upload button here, because Milvus stores vectors,
  not documents.
- Once it reaches *running*, open its connection details and copy the **host,
  port, user, and password** into a scratch cell — you'll pass these to
  `pymilvus` when you load the PDF from the watsonx.ai notebook later.

> **Shared instance?** If you're sharing one watsonx.data instance, you can still
> each create your own engines, or one person creates a set that everyone
> associates with. The SQL and code below are identical either way.

> 📎 Reference — [Milvus — install, connect, and manage collections](https://milvus.io/docs)

### 4 · Ingest the dataset into an Iceberg table

- Open **Data manager**. Inside your `iceberg_data` catalog, create a schema to
  hold the data — this lab assumes **`marine`**. A schema is a labeled folder for
  related tables.
- Choose **Create table from file** and upload
  [`cod_landings_nl.csv`](../../data/cod_landings_nl.csv).
- Name the table **`cod_landings_nl`**. Review the inferred column types — `year`
  and `licensed_fishers` as integers, `landings_tonnes` as a double,
  `fishery_status` as text — and adjust if needed before finishing.
- Finish. watsonx.data registers it as an Iceberg table in your catalog:
  queryable in place, not copied into the engine.

> 📎 Reference — [Iceberg table format — overview](https://iceberg.apache.org/)

### 5 · Run federated SQL

Open the query workspace, select your Presto engine, paste the query, and run it:

```sql
SELECT year, landings_tonnes, licensed_fishers, fishery_status
FROM iceberg_data.marine.cod_landings_nl
WHERE year BETWEEN 1955 AND 2024
ORDER BY year;
```

You should get one row per year from 1955 to 2024, including the 1992 row flagged
with the moratorium status. If the query errors on the table name, confirm the
catalog/schema you created matches `iceberg_data.marine` or adjust the
fully-qualified name.

> **What the platform is doing:** Presto is querying the table where it lives,
> through the catalog. If the data spanned multiple sources, the same engine would
> federate the query with no copies — the 'no ETL' value a DIY stack makes you
> build and maintain yourself.

> 📎 Reference — [Presto — SQL query reference](https://prestodb.io/docs/current/sql.html)

## watsonx.ai · Connect to the AI

**30 minutes.** Point the AI runtime at the same catalogued data — without moving
it. Register the governed connection, read the table through it from the notebook
with the Python SDK, then load the background PDF into the Milvus you created.

### 1 · Create the governed connection

- In your watsonx.ai project, go to **Assets → New asset → Connection**, and
  choose **watsonx.data (Presto)** as the connection type.
- Supply the host, port, and credentials for your Presto engine (from the
  engine's *Connect* panel in watsonx.data), set the SSL/HTTPS option, and name
  the connection `watsonx-data-lakehouse`.
- **Test and save.** This registers the catalogued data source as a governed
  asset in the project — anyone with access reads it through the project's access
  controls, not by holding a copy.

> 📎 Reference — [watsonx-ai-samples — connecting to data from a notebook](https://github.com/IBM/watsonx-ai-samples)

### 2 · Load the catalogued table through the connection

Point the Presto Python client at the same engine, and define a helper that runs
a query and returns a dataframe:

```python
import prestodb, pandas as pd
presto = prestodb.dbapi.connect(
    host=PRESTO_HOST, port=PRESTO_PORT, user=PRESTO_USER,
    catalog='iceberg_data', schema='marine',
    http_scheme='https',
    auth=prestodb.auth.BasicAuthentication(PRESTO_USER, PRESTO_PWD))
def run_sql(sql):
    cur = presto.cursor(); cur.execute(sql)
    cols = [d[0] for d in cur.description]
    return pd.DataFrame(cur.fetchall(), columns=cols)
run_sql('SELECT count(*) AS n FROM cod_landings_nl')
```

The test query should return a single count row — the AI runtime is now reading
your catalogued table in place. If authentication fails, re-copy the credentials
from the engine's Connect panel; if the host is unreachable, confirm the engine
is in the *running* state.

> 📎 Reference — [prestodb — Python client (install & usage)](https://github.com/prestodb/presto-python-client)

### 3 · Load the PDF into your vector database and search by meaning

This is the step people look for a button for in watsonx.data and don't find —
because turning a document into something Milvus can store is a watsonx.ai job.
First, read and chunk the PDF:

```python
from pypdf import PdfReader
reader = PdfReader('docs/cod_background.pdf')
pages  = [p.extract_text() or '' for p in reader.pages]
full   = '\n'.join(pages)
# simple fixed-size chunks (~500 chars) with a little overlap
chunks, step, size = [], 400, 500
for i in range(0, len(full), step):
    piece = full[i:i+size].strip()
    if len(piece) > 50: chunks.append(piece)
print(len(chunks), 'chunks from the PDF')
```

The overlap (step of 400 over a 500-char window) keeps sentences that straddle a
boundary searchable from either chunk.

> 📎 Reference — [pypdf — extract text from a PDF](https://pypdf.readthedocs.io/)

Embed the chunks with the watsonx.ai model and insert them into your Milvus
collection (host/port/credentials from the Milvus connection details you copied
earlier):

```python
from ibm_watsonx_ai.foundation_models import Embeddings
from pymilvus import connections, Collection, FieldSchema, CollectionSchema, DataType
emb = Embeddings(model_id='ibm/slate-125m-english-rtrvr',
                 api_client=client, project_id=PROJECT_ID)
vectors = emb.embed_documents(texts=chunks)
connections.connect(host=MILVUS_HOST, port=MILVUS_PORT,
                    user=MILVUS_USER, password=MILVUS_PWD, secure=True)
schema = CollectionSchema([
    FieldSchema('id', DataType.INT64, is_primary=True, auto_id=True),
    FieldSchema('text', DataType.VARCHAR, max_length=4000),
    FieldSchema('vector', DataType.FLOAT_VECTOR, dim=len(vectors[0]))])
col = Collection('cod_docs', schema)
col.insert([chunks, vectors])
col.create_index('vector', {'metric_type':'L2','index_type':'AUTOINDEX'})
col.load()
```

Now search the PDF by meaning:

```python
q = emb.embed_query(text='what happened to the fishery in the early 1990s?')
hits = col.search([q], 'vector', {'metric_type':'L2'}, limit=3,
                  output_fields=['text'])
for hit in hits[0]: print(round(hit.distance, 2), hit.entity.get('text')[:140])
```

It returns the most relevant passages **by meaning**, not by keyword match — so a
query about the early 1990s surfaces the moratorium passage even if those exact
words never appear. watsonx.ai did the vectorizing and the vectors landed in the
governed Milvus you provisioned — the document never left your environment. If
the search returns nothing, confirm `col.load()` ran and that the embedding
dimension in the schema matches `len(vectors[0])`.

> **No-code alternative:** watsonx.ai also has a **vector index** asset: create
> one, upload the PDF, pick the embedding model, and point it at this same Milvus
> — it chunks and embeds for you. That's the point-and-click path (and the one the
> [non-technical track](../non-technical/README.md) uses); the code above is the
> same thing with the lid off.

> 📎 Reference — [watsonx.ai Embeddings — embed_documents / embed_query](https://ibm.github.io/watsonx-ai-python-sdk/fm_embeddings.html)

## Ask a question, get a visual

**30 minutes · the payoff.** You ask in plain English, Granite turns the question
into SQL and runs it on your catalogued data, then generates the matplotlib code
that draws the chart. The model only ever sees the schema and your question —
never the rows.

### 1 · Let Granite write the query (text-to-SQL)

```python
from ibm_watsonx_ai.foundation_models import ModelInference
granite = ModelInference(model_id='ibm/granite-3-8b-instruct',
    api_client=client, project_id=PROJECT_ID,
    params={'decoding_method':'greedy', 'max_new_tokens':200})
schema   = 'cod_landings_nl(year INT, landings_tonnes DOUBLE, '\
           'licensed_fishers INT, fishery_status VARCHAR)'
question = 'cod landings in tonnes for every year, ordered by year'
prompt = f'''Translate the question into ONE Presto SQL query.
Table: iceberg_data.marine.{schema}
Rules: SELECT only, no DDL/DML, add LIMIT 1000. Return ONLY the SQL.
Question: {question}'''
sql = granite.generate_text(prompt=prompt).strip().strip('`').strip()
print(sql)
```

**Validate before you run it — never execute model-generated SQL blind:**

```python
low = sql.lower()
assert low.startswith('select'), 'Not a SELECT'
assert not any(k in low for k in [' insert',' update',' delete',
       ' drop',' alter',' create',' merge']), 'Mutation blocked'
df = run_sql(sql)
df.head()
```

Those two asserts are the whole safety story: they guarantee the generated
statement is read-only before it ever touches the engine. In production you'd
extend the check (parse the statement, enforce an allow-list of tables, cap the
row count), but the principle is the same — validate model output, then run it.

> 📎 Reference — [watsonx.ai ModelInference — generate_text](https://ibm.github.io/watsonx-ai-python-sdk/fm_model_inference.html)

### 2 · Let Granite generate the chart

```python
prompt = f'''You are a Python data-viz assistant. A pandas dataframe `df`
has columns: {list(df.columns)}.
Write matplotlib code to plot landings_tonnes vs year as a line chart,
add a vertical marker and label at 1992 (the cod moratorium),
give it a clear title, and call plt.show(). Return ONLY code.'''
generated = granite.generate_text(prompt=prompt)
print(generated)
```

Review the generated code (good habit — never run model output blind), then
execute it:

```python
import matplotlib.pyplot as plt
exec(generated)   # read it first, then run
```

The chart renders: the late-1960s peak (~800k tonnes), the decline, and the 1992
collapse marked on the axis. If `exec` raises an error, read the generated code —
the model occasionally references a column name that differs from `df.columns`;
fix the name (or re-prompt with the exact column list) and run again.

> **Analytical follow-up:** change `question` in step 1 to something analytical —
> *'average landings per decade and the peak year in each decade'* — re-run
> text-to-SQL, then let Granite re-plot the new dataframe. The whole pipeline
> flexes to a new question without you writing SQL or plotting code by hand.

> 📎 Reference — [Matplotlib — pyplot tutorial](https://matplotlib.org/stable/tutorials/pyplot.html)

### The sensitive-data pivot

The cod data is public. Re-run the whole pipeline in your head with the table
swapped for genomics data, student records, or unpublished research, and the PDF
for a confidential report. Every step is identical — and at no point did the data
leave your organization's environment or reach an outside model service.

You could rebuild the boxes with Postgres + Jupyter + a hosted API. What you
can't cheaply rebuild is that guarantee, plus one governance and lineage fabric
across both the data and the AI.
